# MimIR

C++23/CMake project: graph-based intermediate representation ("MimIR") with its own surface syntax (Mim, `*.mim`), an LLVM-emitting backend, and a plugin system.
Complementary instruction sources — don't duplicate them here:

- `.github/instructions/{cpp,cmake,mim}-style.instructions.md` — per-language style rules (see [Style](#style)).
- `docs/coding.md` (contributor guide: build options, include style, debugging), `docs/dev.md` (C++ API idioms), `docs/plugins.md` (plugin how-to), `docs/langref.md` (Mim syntax).
- `CLAUDE.md` is a bridge that imports this file and the three style files; `.github/copilot-instructions.md` only points here.

## Build & test

Assume a `build/` tree configured Debug with testing enabled (Debug builds use `-Og` and enable expensive `MIM_ENABLE_CHECKS` by default):

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON -DMIM_BUILD_EXAMPLES=ON
cmake --build build -j$(nproc)   # binaries land in build/bin (mim, mim-test, mim-regex-test, ...)
```

| Task | Command |
| ---- | ------- |
| Build part | `cmake --build build --target mim` / `libmim` / `mim_all_plugins` |
| All tests | `cmake --build build --target test-all` (lit + roundtrip + unit + py) |
| `lit` suite | `cmake --build build --target lit` |
| One lit test | `cd lit && ../scripts/probe.sh foo.mim` — also accepts `extra/<plugin>/lit/foo.mim`, passes extra args through to lit |
| All unit tests | `ctest --test-dir build --output-on-failure` |
| One unit test | `build/bin/mim-test -tc='World: dependent extract'` (`--list-test-cases`, wildcards; `-nb` to disable the debugger break on failure) |
| Round-trip | `cmake --build build --target test-roundtrip`; single file: `cd lit && ./lit ../build/lit --param roundtrip=mim -a --filter fib.mim` |
| Format/lint | `pre-commit run --all-files` (clang-format + `scripts/check_includes.py` include hook + whitespace) |
| Reproducer from a failure | `./scripts/make_lit_error.sh foo.mim` / `./scripts/make_test_error.sh '<test case>'` |

## Gotchas

- Clone recursively: `submodules/fe` (Mim frontend) and `submodules/nanobind` (Python bindings).
- `BUILD_TESTING=ON` fails to configure without LLVM's `FileCheck` (override with `-DMIM_FILECHECK=<path>`); running lit needs the Python `lit` package. The `ll` backend builds its runtime wrappers with `clang`/`llvm-link` (`MIM_BUILD_LL_RUNTIME`, default ON).
- lit executes the copies **staged into `build/lit/`**, not the working tree. `probe.sh` builds the staging target `mim_lit_tests` first; if you run lit manually, build that target (or `lit`) after editing `lit/*.mim` — else you test a stale file.
- Python bindings are generated by `scripts/gen_nanobind_bindings.py` while building `pymim`, sourcing its parse flags from `build/compile_commands.json` (+ `libclang`). Reconfigure CMake after compiler/flag changes or the generated bindings go stale.
- Include style is enforced (`scripts/check_includes.py --fix`): an artifact uses `"..."` only for its own headers and `<...>` for everything it links against — standard library, `fe`, other plugins. After `--fix`, re-run clang-format on the touched files to regroup includes.
- Plugin codegen: `<plugin>.mim` is machine-readable input — the build runs `mim --bootstrap --output-h/-py/-md` over it to emit `autogen.h` (C++ annex enums + normalizer wiring), a Python `IntEnum`, and a Doxygen page. Generated files live in the build tree only; never check them in. `///` doc comments in a `.mim` are simultaneously the annex docs and the generated plugin page.
- Docs prose and `///` doc comments: one complete sentence per line; don't hard-wrap at 80 columns.
- Debugging: from GDB, `call def->dump()` / `call world().dump()` print IR directly and `p world().gid2def(n)` recovers a `Def` by gid; `source scripts/xdot.gdb` from `~/.gdbinit` adds DOT graph commands. CLI: each `-V` raises the log level; `-b <gid>`/`-w <gid>` break when the node is created / sets an operand; `--break-on-alpha`; `--profile {summary,tree,trace}` for phase timing.

## Architecture quick facts

- `libmim` (`src/mim/`, headers in `include/mim/`) is the core library: IR (`Def`, `World`), the Mim AST frontend (`ast/`), rewriting, phases, checks, dumping, and utilities. `src/automaton/` backs the regex subsystem as a separate static library.
- `Driver` is the central runtime object: it owns `Flags`, `Log`, the current `World`, plugin search paths and handles, and the normalizer/stage/backend registries. Plugins, imports, and backend runtimes have three separate lookups (`Driver::plugin_paths`/`import_paths`/`rt_paths`): `-P`/`-I` add plain directories, while `--prefix-path`, the install prefix, and the tree `libmim` came from add prefix roots deriving `<root>/<libdir>/mim`, `<root>/<datadir>/mim`, and `<root>/<libdir>/mim/rt`.
- The `mim` CLI (`src/mim/cli/main.cpp`) is thin glue around `Driver`: parse Mim → compile into the `World` → `optimize(World&)` → emit whatever `--output-*` asks for. Plugins load on demand via `plugin` directives or `-p`/`--plugin`; `--output-h`/`--output-py` bootstrap plugin headers and exit before compilation. A `plugin` directive takes its `.mim` from the directory the library was loaded from, so both halves always pair up.
- A plugin is two halves that must stay in sync under one name: `<plugin>.mim` (public annex surface) and `libmim_<plugin>` (exports `mim_get_plugin` to register normalizers, stages, and backends). Names: letters/digits/underscores, max 8 chars.
- Out-of-tree plugins under `extra/*/CMakeLists.txt` are auto-discovered at configure time; their lit tests are staged into `lit` and unit tests become `mim-<plugin>-test`. Create new plugins with `./scripts/new_plugin.py [--extra]`; the in-tree `demo` plugin (`src/mim/plug/demo/`) is the minimal template.
- Optimization is phase-driven (`Phase`/`RWPhase`/`PhaseMan`, with `Analysis` for fixed points); the old `Pass`/`PassMan` machinery is gone — don't reintroduce it or ad hoc whole-program traversals. `optimize(World&)` looks for an entry point (`_compile`, `_default_compile`, or any nullary external returning `compile.Phase`), resolves stages from the plugin registry, and runs the pipeline; without an entry point optimization is skipped. `RWPhase` rebuilds the old world into a new inherited world and swaps them at the end.
- Tests come in two layers: `lit/` drives the CLI end-to-end with `RUN:` lines plus `FileCheck`, and `test/*.cpp` exercises library APIs with [doctest](https://github.com/doctest/doctest) (`mim-test`, `mim-regex-test`). A third-party plugin's `extra/<plugin>/test/*.cpp` are auto-discovered into `mim-<plugin>-test` the same way its `lit/` tests are staged.

## Core IR invariants

- Keep the immutable/mutable `Def` split: non-binders are hash-consed and normalized on construction, whereas mutables are created first and filled in later to support recursion and variables.
- Terms and types live in the same `World` graph, so type-level computation goes through the same normalization and sharing as ordinary terms.
- Annexes and external mutables are the world roots that analyses and `RWPhase` traverse; `Cleanup` removes whatever is unreachable from them.

## Comments

Comments are scarce. The default is **no comment**.

Comment only when the code itself cannot reasonably express the information.

- Comment **why**, not what the code does.
- Prefer a better name, structure, or API over a comment.
- Keep comments to **one short sentence**, normally one line.
- When a comment spans multiple lines, use **one complete sentence per line**. Do not wrap a single sentence across multiple lines merely to fit a line-length limit.
- A comment should convey one fact only: an invariant, non-obvious constraint, algorithmic reason, or important external reference.
- Do not explain the implementation, summarize a function, or provide a narrative of its control flow.
- Match the comment density and brevity of the surrounding code. **Never increase comment density.**
- Do not add documentation-style prose, introductions, conclusions, or motivational/explanatory language.
- Do not use rhetorical contrasts such as `"X" -> "Y"`, `"instead of X"`, or `"from X to Y"` to explain an optimization.
- Do not add comments describing the change itself ("now handles X", "renamed from Y"); that belongs in the commit message.
- Do not add banner or section-header comments.
- Do not add a comment if deleting it would leave the code equally correct and understandable.
- A comment that restates the code is worse than no comment:
  ```cpp
  vec.push_back(x); // BAD: "put x into the vector"
  ```

**Hard limit:** Do not write multi-line comments unless the user explicitly asks for documentation or the comment is required to document a non-obvious invariant that cannot be stated briefly.

Before adding a comment, ask:
1. Is this information necessary?
2. Is it already apparent from the code or names?
3. Can it be expressed in one short sentence?
If the answer to 1 or 3 is no, do not add the comment.
